### 1.4 Supabase access — the critical finding
- **Two client factories:** `lib/supabase.ts` (browser anon) and `lib/supabase-server.ts` (**service-role, bypasses RLS**), plus `@supabase/ssr` session helpers in `lib/supabase-auth-server.ts` / `lib/supabase-auth.ts`. Bot has its own `bot/supabase-admin.ts`.

It is the pattern to replicate for every domain. `hifz/` has partial repos (`review-log.ts`, `stats.ts`, `study-progress.ts`, `scheduler.ts`).

## 2. Target layout

```
src/
  features/                    # one folder per domain; owns routes-logic + components + domain lib + repository
    read/                      # mushaf reading chrome, audio dock, navigation (NOT the QCF renderer internals)
      components/
      domain/                  # pure logic (readMode, navigation, jump-targets)
      data/                    # read-domain repository (surah/ayah/word/page reads)
      index.ts                 # PUBLIC INTERFACE (barrel) — the only import surface
    hifz/
    faham/
    tema/
    tasmi/                     # client lib only; talks to tasmi-server via app/api proxy
    auth/                      # Supabase Auth (scaffold today → activated in Phase 2)
    license/                   # NEW in Phase 2; empty scaffold now (dir + index.ts + repository stub)
      index.ts
  data/                        # THE repository layer — the ONLY place that imports a Supabase client
    supabase/                  # client factories: server (service-role), rls (session-scoped), browser
    repositories/              # typed repositories, per domain, re-exported by each feature's data/
  ui/                          # design-system layer (structure now, restyle in Phase 2)
    tokens/                    # token contract (CSS vars); placeholder values now
    primitives/                # Button, Card, Sheet, etc. — extracted, not restyled
    theme/                     # dark/light color-mode (the UI "theme", NOT tema)
    styles/                    # globals.css, mushaf-live.css
  mushaf/                      # SACRED — QCF renderer, glyphs, layout, assets. WRAP, never rewrite.
  shared/                      # genuinely cross-cutting: types/database, fsrs, activity, ratelimit, pwa infra
    pwa/                       # service-worker registration, offline engine, download engine
  bot/                         # Telegram bot (relocated as-is; own supabase-admin; not a web feature)
  app/                         # Next route shells only — import feature public interfaces, render, done
```

**Rules encoded by the layout**
- `features/*` never import each other's internals — only via `features/x/index.ts`.
- `data/` is the **only** importer of a Supabase client. Features import repositories, never `supabaseServer`.
- `mushaf/` is import-only from `features/read` and `features/hifz`; its internals are frozen (sacred).
- `app/` shells stay thin (current avg ~5 lines of imports + render — preserve this).

### 4.2 Typed boundaries
Every `features/x/index.ts` exports **typed** interfaces only. Every repository returns a **typed domain object** (never a raw Supabase row / `any`). Cross-module handoffs carry an explicit type from `shared/types` or the feature's `domain/types.ts`.

### 4.3 Immutability
No in-place mutation across module boundaries; repositories return fresh objects; state updates create new objects (already the norm — only 1 context).

### 4.4 No cross-feature imports except via public interface
Enforce with an ESLint boundary rule (`no-restricted-imports`): `features/a/**` may not import `features/b/**` except `features/b` (barrel). `data/` importable by any feature; **no feature-Supabase-client import** outside `data/`. `mushaf/` internals private behind `mushaf/index.ts`.

- **Behavior changes** — Phase 1 is byte-for-byte behavior-preserving. Any behavior delta is a bug.

- **Mushaf/QCF rendering internals** — `MushafPageView`, glyph/layout/font/asset resolution are **SACRED**. Relocate + wrap behind `mushaf/index.ts`; **never rewrite** logic. Exempt from the 400-LOC rule.

- **Tasmi Python server** logic — reconcile source per Phase-0, but no rewrite; deploy is Phase-2 Lane C.
- **New features** — auth activation, license, payment webhook are **Phase 2**. Phase 1 only creates their **seams** (empty scaffolds + repository stubs).
- **Test-coverage expansion** beyond boundary-contract tests — building the missing e2e/component suite is valuable but is a Phase-2/3 concern; Phase 1 relies on the Phase-0 screenshot baseline as the safety net.
